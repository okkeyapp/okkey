# 6.26 Crypto Emergency Response Runbook

This runbook defines emergency response procedures for crypto incidents in Core.

## Goal

Provide a repeatable procedure for incidents related to compromised or weakened
crypto algorithms, implementations, rollout controls, and transport posture.

## Scope

- Incident triage and severity assignment.
- Emergency containment via rollout gates and policy controls.
- Profile-level decisioning using the `6.25` matrix.
- Rotation/rewrap sequencing for incident recovery.
- Communication workflow, SLA, and return-to-normal criteria.

Out of scope:

- Live production emergency switch execution.

## Incident classes

| Class | Trigger examples | Default severity |
| --- | --- | --- |
| Policy drift | Unexpected profile allowed in `stage`/`prod`, matrix mismatch | Sev-1 |
| Downgrade pressure spike | sustained `policy_violations_total(reason=downgrade)` | Sev-1 |
| Rotation instability | sustained `rotation_failures_total` in critical write paths | Sev-2 |
| Crypto implementation risk | newly disclosed vulnerability in active profile implementation | Sev-1 |
| Transport crypto risk | edge TLS/KEX weakness requiring compatibility rollback | Sev-1 |

Severity model:

- `Sev-1`: production security posture at risk or broad write-path impact.
- `Sev-2`: contained instability with mitigation available.
- `Sev-3`: low-risk anomaly, no immediate security posture degradation.

## Roles and ownership

| Role | Responsibilities |
| --- | --- |
| Incident commander | Owns timeline, severity, go/no-go decisions, and closure criteria. |
| Security lead | Assesses cryptographic risk, approves containment profile and recovery path. |
| Backend on-call | Executes rollout gate changes and validates API behavior under containment. |
| Infra/SRE lead | Executes transport/edge actions when 6.19 path is triggered. |
| Communications owner | Publishes internal/external status updates and ensures approved wording. |
| Release owner | Authorizes staged resume and records final operational sign-off. |

## SLA targets

| Milestone | Target SLA |
| --- | --- |
| Incident acknowledgement after alert | <= 10 minutes |
| Severity assignment and owner confirmation | <= 20 minutes |
| Initial containment decision (global or scoped freeze) | <= 30 minutes |
| First internal status update | <= 30 minutes |
| Subsequent internal updates while Sev-1 active | every 30 minutes |
| First external status update (if customer-facing impact) | <= 60 minutes |
| Draft postmortem checklist created | <= 24 hours after stabilization |
| Final postmortem published | <= 5 business days |

## Response flow

### 1) Detect and classify

1. Open incident timeline and assign Incident commander.
2. Classify using incident classes and severity model above.
3. Capture triggering metrics and evidence snapshot:
   - `crypto.policy_violations_total`
   - `crypto.rotation_failures_total`
   - `crypto.operation_total`
   - `crypto.capability_coverage_total`

### 2) Contain

Use `6.22` runtime gates:

1. Set `CRYPTO_ROLLOUT_STATE=stop`.
2. Choose containment scope:
   - global freeze: `CRYPTO_ROLLOUT_STOP_WRITE_PATHS=*`;
   - scoped freeze: set only affected paths.
3. Validate blocked writes return `CRYPTO_ROLLOUT_PAUSED`.
4. Confirm no sensitive data leakage in logs/metrics.

### 3) Decide profile action using `6.25`

1. Validate current environment policy against canonical matrix (`6.25`).
2. For `stage`/`prod`, do not introduce profile changes that violate matrix rules.
3. If incident requires profile disable sequencing, document:
   - impacted environment;
   - affected profile/version;
   - compatibility window and expiration.
4. Record decision with Security lead and Release owner approval.

### 4) Recovery path (rotation/rewrap and transport)

1. If key material exposure or stale wraps are suspected, trigger `6.10`-aligned
   rotation/rewrap sequence under containment.
2. If transport posture is implicated, execute `6.19` rollback/runbook procedures.
3. Resume in stages:
   - keep `stop` with narrowed blocked paths;
   - monitor stabilization window;
   - switch to `resume` only after sign-off.

### 5) Communication

Required channels:

- internal incident room;
- engineering/security update channel;
- status-page/customer channel (if external impact exists).

Communication constraints:

- disclose impact and mitigation status;
- do not disclose key material details, exploit specifics, or sensitive internals;
- align wording with zero-knowledge and policy boundaries.

## Return-to-normal criteria

All conditions must pass:

1. Root cause identified and mitigated.
2. Required containment gates are removed in staged order.
3. Metrics stabilized for agreed observation window (minimum 30 minutes for Sev-1).
4. No active policy violations against `6.25` matrix.
5. Rotation/rewrap validation completed when incident class requires it.
6. Security lead + Release owner sign-off recorded.
7. Postmortem checklist created and owner assigned.
