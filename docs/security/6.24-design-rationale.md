# 6.24 Design Rationale (High-Risk Crypto Decisions)

This document records rationale for high-risk decisions relevant to external crypto review.

## Decision 1: Production uses `v2` only for encrypted writes

- Decision:
  - `stage/prod` write paths enforce `crypto_version=v2`.
- Why:
  - Prevent weak-profile persistence and avoid post-launch crypto migration obligations.
- Alternatives considered:
  1. Keep mixed `v1/v2` in production for backward compatibility.
  2. Silent fallback from v2 to v1 for unsupported clients.
- Why alternatives rejected:
  - Increases downgrade surface and weakens first-day Q-Day posture.
- Residual risk:
  - Compatibility pressure for legacy clients in prod.
- Compensating controls:
  - Explicit policy errors (`CRYPTO_PROFILE_NOT_ALLOWED`, `CRYPTO_DOWNGRADE_NOT_ALLOWED`).
  - Internal-only migration tooling for pre-prod/test.

## Decision 2: Rust/WASM-only crypto path (no JS/TS fallback)

- Decision:
  - Hybrid/PQ primitives run only in Rust engine through WASM bindings.
- Why:
  - Single cryptographic implementation and stricter contract consistency.
- Alternatives considered:
  1. Keep JS/WebCrypto fallback for resilience.
  2. Mixed implementation by platform.
- Why alternatives rejected:
  - Inconsistent behavior and larger audit surface for correctness proofs.
- Residual risk:
  - Build/distribution dependency on WASM artifact integrity.
- Compensating controls:
  - Cross-layer contract tests and fuzz/property suites.
  - Supply-chain controls implemented under `6.27` (reproducibility + provenance + attestation).

## Decision 3: Anti-downgrade via stream/vault monotonic floors

- Decision:
  - Enforce monotonic floor on event schema (`payload_schema_version`) and vault crypto version.
- Why:
  - Prevent rollback to weaker encrypted artifacts across sync/replay paths.
- Alternatives considered:
  1. Per-request policy check only.
  2. Client-only downgrade prevention.
- Why alternatives rejected:
  - Server must remain final policy gate; client-only checks are bypassable.
- Residual risk:
  - Complex race/conflict conditions in multi-device sync.
- Compensating controls:
  - Rotation atomicity + replay invariants tests.
  - Security suite coverage for replay/rollback/mixed-device cases.

## Decision 4: Hybrid envelopes and signatures for critical integrity

- Decision:
  - Use canonical hybrid envelope and hybrid signature verification for critical operations.
- Why:
  - Preserve confidentiality and authenticity under Q-Day transition posture.
- Alternatives considered:
  1. ECC-only signing and wrapping for first release.
  2. Deferred signature verification to later phase.
- Why alternatives rejected:
  - Weakens integrity guarantees during transitional period.
- Residual risk:
  - Schema and canonicalization drift across layers.
- Compensating controls:
  - Canonical envelope contracts in architecture + API docs.
  - Rust/WASM/TS contract tests and fuzz triage process.

## Decision 5: Rollout controls and stop/resume gates

- Decision:
  - Keep rollout state/mode controls (`strict`/`compat`, stop/resume paths) with observability.
- Why:
  - Allow controlled rollout and quick containment of policy regressions.
- Alternatives considered:
  1. Hardcoded strict-only rollout without control gates.
  2. Manual toggles without metrics.
- Why alternatives rejected:
  - Operationally fragile and harder to audit incident response.
- Residual risk:
  - Misconfiguration in CI/runtime env matrix.
- Compensating controls:
  - Rollout observability evidence and runbooks (`6.22`).
  - Policy matrix hardening tracked under `6.25`.
