# 6.19 TLS/Transport Q-Day Runbook (Core)

This runbook defines the target transport security posture for `stage` and `prod`
with Q-Day constraints, plus rollout and rollback procedures.

Scope:

- edge/ingress TLS policy for client -> edge traffic;
- certificate lifecycle and trust requirements;
- staged rollout and emergency rollback procedure.

Out of scope:

- full infra implementation details for a specific ingress stack.

## Inputs and hard constraints

- `docs/release_policy_qday.md`
- `docs/architecture/14_crypto_v2_qday.md`
- `docs/architecture/08_security_model.md`
- `docs/architecture/09_self_hosting.md`
- `docs/storage_and_infrastructure.md`
- task dependency `6.25` policy matrix (`dev`/`stage`/`prod` transport policy source).

Non-negotiable constraints:

- no silent downgrade to weaker production posture;
- `stage`/`prod` production traffic follows Q-Day baseline from release policy;
- change management must include explicit rollback triggers and operator runbook.

## Target-state transport profile

### Baseline by environment

| Environment | TLS baseline | KEX posture | Compatibility mode |
| --- | --- | --- | --- |
| `dev` | TLS 1.2+ allowed for local tooling; TLS 1.3 preferred | classical or hybrid for testing | allowed |
| `stage` | TLS 1.3 required for validation lanes | hybrid preferred; strict-hybrid lane required for gate checks | time-boxed and explicit |
| `prod` | TLS 1.3 required on public edge | hybrid required on default edge policy | exceptional, explicit, time-boxed |

### Edge/ingress requirements

1. TLS policy is enforced at edge/ingress, not delegated to app handlers.
2. `prod` default listener uses a hybrid-capable key exchange profile.
3. Any compatibility listener/profile must be:
   - explicitly configured (no automatic fallback),
   - isolated by route/domain/listener policy,
   - protected by allowlist and expiration window.
4. Reject configuration that allows silent downgrade from strict to compatibility
   mode for the same default production route.
5. Keep handshake and policy decision telemetry at edge with redaction-safe logs.

### Certificate policy

- Certificates must be issued by a trusted CA chain accepted by target clients.
- Certificate automation is mandatory (provision + renew + deploy).
- Renewal safety window must be documented (recommended <= 60 days remaining).
- Private keys stay in approved secret storage and never in VCS.
- Revocation response path must be documented (replace certs, rotate keys, verify).
- SANs/domains for API and web endpoints must match deployment targets.

### Proxy and internal transport requirements

- External traffic is HTTPS-only.
- Ingress to upstream services must be private-network only; TLS/mTLS policy is
  defined by deployment mode and risk level.
- WebSocket/sync transport must remain enabled under the same edge TLS policy.
- Security headers and protocol constraints are managed at edge policy level.

## Rollout phases

### Phase 0: Preparation

- Map current edge listeners, TLS versions, and certificate automation state.
- Confirm dependency `6.25` policy matrix values for `stage` and `prod`.
- Prepare compatibility allowlist and sunset criteria before any production move.

Exit criteria:

- inventory complete, owners assigned, rollback tested in non-prod.

### Phase 1: Staging dry-run

- Apply target policy in staging edge/ingress.
- Run handshake validation for strict-hybrid profile and compatibility profile.
- Verify sync/WebSocket behavior and client compatibility matrix.
- Capture telemetry baselines for handshake errors and fallback attempts.

Exit criteria:

- checklist pass, no unresolved critical incompatibilities, rollback drill passed.

### Phase 2: Production canary

- Enable strict profile on limited traffic slice or dedicated canary endpoint.
- Keep compatibility profile disabled by default, enable only by explicit allowlist.
- Monitor handshake success rate, error spikes, and latency.

Exit criteria:

- stable metrics for agreed observation window, no security policy violations.

### Phase 3: Production full rollout

- Promote strict profile to default production edge policy.
- Keep compatibility exception path time-boxed with published sunset date.
- Record final configuration and approval evidence.

Exit criteria:

- full traffic on strict profile, exception path (if any) tracked and expiring.

## Rollback runbook

### Rollback triggers

Trigger rollback when one or more conditions are met:

- sustained handshake failure above agreed SLO threshold;
- critical client segment lockout without approved mitigation;
- certificate or trust-chain incident that blocks availability;
- security signal indicating unexpected downgrade behavior.

### Rollback procedure

1. Incident commander declares rollback and opens incident timeline.
2. Switch edge policy from strict profile to pre-approved compatibility profile.
3. Keep HTTPS/TLS requirements in place; do not roll back to insecure transport.
4. Validate service recovery (API, web, sync/WebSocket) and error-rate recovery.
5. Preserve forensic logs and config diff for post-incident review.
6. Create remediation ticket with owner and deadline before re-rollout.

### Rollback guardrails

- rollback uses only pre-approved configuration artifacts;
- emergency changes are peer-reviewed retrospectively in postmortem;
- no emergency path may violate zero-knowledge or crypto policy boundaries.
