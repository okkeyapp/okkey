## Auth Surface Inventory (Current Baseline)

| Surface | Current flow | Crypto/material class | Baseline posture | Boundary |
| --- | --- | --- | --- | --- |
| Email challenge login | `/auth/email/start|resend|confirm` | server-security (OTP secret lifecycle, anti-bruteforce controls) | Core default sign-in first factor | Core |
| Passkey login | WebAuthn challenge + assertion verify | transport + auth-proof verification | Core supports passkey login; no legacy profile exception | Core |
| Device approval | existing device / email / passkey verification | server-security + device binding | Core mandatory for new devices | Core |
| 2FA (second factor) | TOTP + backup codes | server-security (`HMAC-SHA1` RFC6238 scope only) | Core open-source supported second factor | Core |
| WebAuthn as second factor | security key as step-up factor | auth-proof + policy gating | planned outside Core | Enterprise extension |
| SSO federation | OIDC / SAML | transport/integration + assertion validation | not part of Core runtime baseline | Enterprise extension |
| Session bootstrap and proofs | post-auth session issue, rotation, binding | server-security + transport | Core required; must align with `v2` policy constraints | Core |

Notes:
- `vault-data` cryptography stays in Rust/WASM path and is out of scope for auth proofs.
- Auth crypto dependencies remain classified as `server-security` and `transport/integration`.

## Target Q-Day Profile for Auth Surfaces

Policy is aligned with `docs/security/6.25-crypto-policy-matrix.md`.

| Environment | Auth rollout mode | Allowed write profile baseline | Auth policy target |
| --- | --- | --- | --- |
| `dev` | `compat` | `v1` + `v2` (for fixtures/local validation only) | validate migration and mixed capability scenarios without production fallback assumptions |
| `stage` | `compat` | `v2` only for production-like write paths | verify phased auth rollout and boundary controls before strict cutover |
| `prod` | `strict` | `v2` only | no legacy crypto exceptions, no silent downgrade, no enterprise override of core policy |

Core target:
- Keep Core first production release fully functional with email + passkey login,
  TOTP/backup codes second factor, and session/device controls.
- Keep cryptographic policy ownership in Core for all auth write-path decisions.

Enterprise target:
- Deliver SSO/SAML/OIDC and optional WebAuthn second-factor as extension modules.
- Consume Core capability metadata and policy hooks only.
- Never redefine Core crypto profile, downgrade behavior, or legacy exceptions.

## Phased Rollout and Compatibility Modes

### Phase 0: Inventory and policy lock

- freeze auth crypto boundary and ownership mapping.
- ensure docs/contracts do not conflict with `6.20` and `6.25`.

### Phase 1: Compat rollout (`dev`/`stage`)

- deploy auth-surface controls in `compat` mode where needed.
- allow controlled mixed-capability testing in non-production only.
- collect readiness signals: downgrade attempts, capability mismatches,
  session/bootstrap regressions.

### Phase 2: Strict rollout (`prod`)

- enforce strict policy for all production auth write paths.
- block legacy fallback and profile downgrade attempts.
- keep enterprise extensions behind feature interfaces with explicit boundary checks.

## Stop Conditions (Hard Blocks)

Rollout must stop and revert to safe state if any condition is detected:

1. Any auth path introduces production fallback to legacy profile behavior.
2. Any Core or Enterprise change bypasses Core downgrade/policy checks.
3. Session proof or device-binding logic accepts mixed capability in strict mode.
4. Feature flag or license state can bypass crypto policy gates.
