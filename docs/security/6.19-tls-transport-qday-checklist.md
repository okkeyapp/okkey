# 6.19 TLS/Transport Q-Day Validation Checklist

Use this checklist with `docs/security/6.19-tls-transport-qday-runbook.md`.

## A. Staging dry-run checklist

- [ ] `6.25` policy matrix values for transport are referenced in test notes.
- [ ] Staging edge policy is configured to TLS 1.3 baseline.
- [ ] Strict-hybrid profile is enabled and validated.
- [ ] Compatibility profile (if needed) is explicit and time-boxed.
- [ ] Handshake validation completed for:
  - [ ] supported modern clients;
  - [ ] expected legacy clients under compatibility mode;
  - [ ] negative path (unsupported profile rejected as expected).
- [ ] Web and API endpoints succeed under target policy.
- [ ] Sync/WebSocket flows succeed under target policy.
- [ ] Edge telemetry confirms no silent fallback behavior.
- [ ] Rollback drill completed in staging.

## B. Production readiness checklist

- [ ] Security owner approved target profile and downgrade boundaries.
- [ ] Infra/SRE owner approved ingress/certificate operational readiness.
- [ ] Release owner approved rollout window and rollback ownership.
- [ ] Certificate automation validated (renewal, deploy, trust chain checks).
- [ ] Alerting defined for handshake error spikes and cert incidents.
- [ ] Incident runbook linked and on-call aware of rollback triggers.
- [ ] Canary scope and observation window documented.
- [ ] Compatibility exceptions (if any) have:
  - [ ] explicit allowlist,
  - [ ] sunset date,
  - [ ] migration owner.

## C. Production rollout validation

- [ ] Canary rollout started with strict profile.
- [ ] Handshake success rate remains within agreed SLO.
- [ ] API, web, and sync latency/error budgets remain healthy.
- [ ] No unauthorized downgrade events observed.
- [ ] Full rollout promoted after canary window success.
- [ ] Post-rollout evidence captured and linked.

## D. Rollback execution checklist

- [ ] Trigger condition documented with timestamp and owner.
- [ ] Rollback announced in incident channel.
- [ ] Edge switched to pre-approved compatibility profile.
- [ ] HTTPS-only posture remains enforced after rollback.
- [ ] Service recovery validated (API/web/sync).
- [ ] Post-incident action items created before re-rollout.

## F. Validation command pack (example)

Use these commands as a baseline and adapt endpoints/ciphers to your edge stack.

TLS version and certificate chain:

```bash
openssl s_client -connect api.example.com:443 -tls1_3 -servername api.example.com </dev/null
```

Protocol/cipher scan (quick smoke):

```bash
curl -I --tlsv1.3 https://api.example.com/health
curl -I --tls-max 1.2 https://api.example.com/health
```

Expected:

- first command succeeds for production edge;
- second command must fail for strict profile (or succeed only on explicit compatibility endpoint).

WebSocket/sync smoke:

```bash
curl -i --http1.1 -N \
  -H "Connection: Upgrade" \
  -H "Upgrade: websocket" \
  -H "Sec-WebSocket-Version: 13" \
  -H "Sec-WebSocket-Key: SGVsbG8sIHdvcmxkIQ==" \
  https://api.example.com/sync/ws
```

Rollback validation smoke (after switch to compatibility profile):

```bash
curl -I https://api.example.com/health
```

Expected:

- availability restored;
- alert noise returns to baseline;
- incident timeline includes trigger + rollback timestamp + owner.
