# 6.21 Key Lifecycle and Zeroization Policy (Core)

## Purpose

buffers across Core clients and backend security crypto surfaces.

## Secret Classes

| Class | Examples | Core rules |
| --- | --- | --- |
| `vault-data key material` | VaultKey shares, item encryption keys, user private bundles, personal metadata keys | Generate on client, keep in memory only for operation scope, wipe temporary buffers after use, never log/export raw bytes |
| `server-security secrets` | session bearer token plaintext window, sealed TOTP secret plaintext window, backup-code plaintext before hashing | Keep in memory only for current request step, persist only hashed/sealed forms, wipe temporary buffers, redact request-visible tokens/codes |
| `transport/integration secrets` | provider API keys, SMTP credentials, deployment TLS key references | Never commit to VCS, load from env/secret manager, redact logs, rotate by ops policy |

## Lifecycle State Model

All sensitive material in Core follows this state machine:

`generated -> active -> rotated_or_replaced -> wiped -> reference_dropped`

State invariants:

1. `generated`: secret exists only in function scope where created.
2. `active`: secret is used for a bounded operation (encrypt/decrypt/verify/sign, hash/seal).
3. `rotated_or_replaced`: old secret is no longer authoritative for new writes.
4. `wiped`: mutable byte buffers are overwritten (`fill(0)`) as best-effort.
5. `reference_dropped`: no further references remain in code path.

## Zeroization Rules

### Mandatory

- All temporary mutable buffers (`Uint8Array`, `Buffer`) that contain secret
  material MUST be overwritten after use.
- SDK/client code MUST use shared guardrail helpers for wipe-on-finally.
- Backend security crypto paths MUST wipe decrypted TOTP/session-related buffers
  immediately after verification/serialization boundary.
- Sensitive values MUST NOT be included in logs, URL query output, or error
  payloads.

### Explicit limitations

- JS/TS runtime provides best-effort memory cleanup only; GC copies are outside
  deterministic control.
- Rust/WASM side remains canonical crypto implementation; when bytes cross
  WASM -> JS boundary, this policy requires best-effort wipe on JS-managed copies.

## Platform Secure Storage Classes

| Platform | Storage class | Allowed secret persistence | Forbidden |
| --- | --- | --- | --- |
| Web | IndexedDB + WebCrypto-backed wrapping where applicable | encrypted vault state, device-scoped share wrappers | raw VaultKey/private bundles in plain `localStorage` |
| Mobile | iOS Keychain / Android Keystore | device share and app secret references | plaintext key material in generic app storage |
| Desktop | OS secure storage + encrypted SQLite state | device secrets and encrypted local state | plaintext key dumps/log snapshots |
| Browser extension | browser extension storage only for wrapped/encrypted state | minimal encrypted cache, short-lived in-memory decrypted material | long-lived plaintext secrets in extension storage sync/local |

## Audit Checklist

1. Secret class is identified (`vault-data`, `server-security`, `transport`).
2. Lifecycle states are explicit in implementation path.
3. Temporary buffers are wiped in `finally` blocks.
4. Stored form is sealed/hashed/encrypted, not plaintext.
5. Logging path redacts sensitive query params and secret-like fields.
6. Tests verify invariants and redaction behavior.

## Test Requirements

- Unit: secret-buffer helpers wipe data as expected.
- Unit: backend helpers wipe temporary buffers in seal/open flows.
- Security: request logger redacts secret query params (`token`, `code`,
  `totp_code`, `backup_code`, capsule key params).
- Integration smoke: critical 2FA/session paths still function while applying
  wipe-on-finally guardrails.
